# Muse challenge: earn trustworthy intraday decision support

Handoff date: **2026-10-04 UTC**. Status: **PROPOSED; implementation and release gates remain open**.

Muse's assignment is to turn this small 0DTE stack into a useful, reproducible research instrument: explain what changed, what was actually knowable at the time, what is missing, and whether an additional feature improves a predefined decision task beyond GRID's existing price, volatility, and GEX information. A reliable null result, an honest unavailable state, and a well designed dashboard are valuable outcomes. This challenge promises neither alpha nor profit.

This document is the task for the Muse/project team to execute later. The current change adds documentation only. Application fixes, collector execution, deployment, production writes, notifications, live orders, funding, credential creation, and scoring-hold release are outside this change. Future work still follows repository instructions and the owner's release workflow. Existing poll intervals do not establish provider entitlement, redistribution rights, or permission to start new polling.

## 2. Operating contract: bounded improvement with review receipts

Start by reading live repository instructions, skills, open PRs and active claims, then create an isolated clean branch from the exact remote base. Recheck heads before reusing the evidence above. Preserve other work. A reviewer is the project controller or designated human; an implementer's self-review is provisional and cannot substitute for acceptance.

Each cycle has **one scoped failure, one minimal patch, its focused regression tests, and one report**. Default budget: 45 minutes, at most 40 tool calls including nested calls and retries, at most two focused test runs after the initial reproduction, zero new paid-provider spend, and at most 256 MiB of new fixtures/results. Reserve time/calls for the receipt. Record actual elapsed time, calls, bytes and cost; a free authorized read is still a tool call. Larger work must be split into explicit subsequent tasks with an approved budget before execution. Do not launch an automatic recurring loop or expand into unrelated findings.

Stop at the first applicable condition: scoped acceptance evidence complete; unresolved dependency or contradictory oracle; missing data/access/rights; failed required check; budget exhausted; or reviewer decision needed. Report `PROVISIONAL`, `ACCEPTED`, `BLOCKED`, or `NULL_RESULT` with the exact reason. Do not retry until a blocker disappears by evidence, silently relax a tolerance, or ask another agent/model for repeated reviews until one approves. No live orders, funding, keys, new provider polling, production repair, deployment or score promotion are authorized by a passing offline stage.

Produce a stable packet such as `artifacts/muse-challenge/<stage>/<cycle-id>/` (a reviewable external store is acceptable for restricted/large data). Include:

- `manifest.json`: Muse base/patch/tested full SHAs; GRID reference SHA; clean/dirty state; test-harness and dependency versions; fixture paths, hashes, license/redistribution status; seeds; clock/calendar assumptions; schema and formula versions; commands, budgets and measured consumption.

Retain accepted packets rather than overwriting a `latest` file. Link each cycle from a small progress ledger. Passing after must address the original failing assertion; an honest quarantine/unavailable result can be the intended fix when inputs cannot support the metric.

### Stage 2: numerical oracle and history durability

Build an independent reference from option value and finite differences; do not copy the production Greek implementation into the oracle. Specify European versus American/discrete-dividend approximation, `r`, `q`, volatility units, contract multiplier, year basis, expiry convention, derivative variable and dealer scenario. Test positive and negative shocks. Preregister absolute/relative tolerances before running the candidate, include a step-size convergence table, and separately bound near-expiry or ill-conditioned cases. Undefined inputs are unavailable, not a mathematically justified zero.

Canonical scenario quantities, for signed dealer contract counts `n_i`, are:

```text
Gamma_i = dDelta_i/dS                          [1/USD]
dealer_gamma = sum(n_i * multiplier_i * Gamma_i) [shares/USD]
exposure_usd_per_1pct = dealer_gamma * S^2 * 0.01
linear_hedge_shares(dS) = -dealer_gamma * dS
linear_hedge_usd(dS) = linear_hedge_shares(dS) * S
vanna = dDelta/dsigma                         [per 1.0 volatility]
one_vol_point = 0.01 absolute volatility
decay_per_hour = -dDelta/dT / (365.25 * 24)    [T in years]
```

The last sign is for passage of clock time with remaining `T` declining; hedge-trade sign then opposes position delta change. Declare another year basis explicitly if used. Finite differences must establish the actual charm formula and sign before applying this conversion. Call/put OI signed as long calls/short puts is a scenario; reverse it, test both-long, both-short and zero inventory, and show the scenario prominently. OI does not identify dealer ownership. Freeze versus refit IV/OI for spot shocks must be stated, with sensitivity bounds.

Use entire future sessions for held-out tests, no random row split. Fit transforms, imputations and thresholds on training only. Tune on validation only. Keep the final test untouched until the specification is locked. Count every tested feature/rule; do not report only the winner.

Required comparisons: a simple time/session/price baseline; GRID's available price/realized-volatility/GEX baseline at the same decision timestamps and coverage; that baseline plus the single Muse candidate; and ablations removing source-identical or redundant inputs. Record shared lineage explicitly. Two transforms of the same delayed chain are not independent confirming votes. If a comparable GRID baseline cannot be obtained lawfully, incremental-value acceptance is blocked.

## 4. Muse dashboard: a concrete professional design brief

This is Muse's dashboard scope. GRID's existing GEX UI is owned elsewhere; define an integration contract and coordinate ownership before requesting a GRID UI change. First recover any Muse dashboard artifact referenced by the builder, including source, screenshots, revision and interaction model. Its absence is a frontend-source blocker, not proof that a particular design is deployed. A synthetic-data prototype can still be reviewed.

Use a cohesive restrained system: slate/ink page background, raised neutral surfaces, one blue accent for navigation, consistent 8px spacing rhythm, generous chart area and tabular numerals. Choose one readable UI font stack, 16px body text and compact but legible labels. Use signed diverging chart colors only for signed exposures; reserve caution/error colors for quality. Direction, modeled state and freshness need text/icons/patterns as well as color. Avoid decorative profit gauges, oversized signal-confidence scores and decimals unsupported by inputs.

Deliver these screens and interactions in the actual Muse frontend:

1. **Session / Now:** clear symbol, expiry and ET session header with a UTC/local time toggle. A persistent trust strip shows quote age, chain age or unknown, receipt/compute times, coverage, source mix and provisional/accepted state. Primary area shows observed price and descriptive levels; scenario exposure cards explain units and dealer sign. Separate observed from modeled sections.
2. **Changes / Replay:** chronological level revisions and alerts with fixed reference, decision time, input hashes/quality and reason. Select a timestamp to reconstruct the exact historical view; pause/step/play with a visible replay mode. Late arrivals and revised data remain identifiable. A provenance drawer answers why each value was available then.
3. **Strike x time:** legible heatmap with strike labels, ET/UTC time axis, explicit `USD millions per 1% move` or the adopted canonical unit, fixed visible scale and sign legend. Use gaps/hatching for missing/stale cells, distinct real-zero styling, and source/model indicators. Hover, keyboard focus or tap reveals contract/strike scope, times, units, sign scenario and quality. Zoom/scroll and date/expiry filters retain context; no interpolation across missing sessions without an explicit modeled layer.
4. **Research / Quality:** collapsible assumptions, accepted formula versions, coverage exclusions, candidate/null-result status and baseline/ablation receipts. A pin heuristic can be shown with component definitions and a heuristic label; it is not a probability or calibrated confidence. Show stale, partial, empty, closed-market, offline and invalid-data states with last-good time and reason, preserving the user's selected session.

Provide a token/style sheet, desktop 1440px and tablet 768px screenshots, phone 390px/320px layouts, interactive prototype or frontend branch, fixture-to-screen manifest, and a short interaction recording. On mobile stack the trust strip/cards, let the heatmap scroll inside its panel, keep core controls reachable, and provide a table alternative. Reuse current history, alerts and builder projections where compatible; changing visuals must not smuggle in changed formulas or silently fix missing data.

## 5. Read-only GRID integration and forward observation

Propose a versioned read-only adapter contract, validated with frozen payloads before any activation. GRID retains collector ownership. Muse consumes existing authorized normalized inputs or archived exports and emits a derived research projection; it does not duplicate collector polling or assume a new provider subscription. Agree exact endpoints/schema versions with the GRID owner; the pinned source above is evidence to reconcile, not a guaranteed deployed API contract.

Envelope requirements: exact upstream revision when available, producer/lineage IDs, payload hash, symbol/expiry/option identity, all source/receipt/available times, delay/quality/coverage, units, model/scenario parameters, formula/schema versions, and derived Muse head. Never overwrite upstream observations, GRID alerts, production stores or score inputs. Missing schema/coverage/rights yields an explicit unavailable projection. Version incompatibility stops the adapter. Identical lineage stays a single information source in evaluations.

Stage 4 freezes a prospective paper-observation protocol: decision record stored before its outcome window; exact available inputs and baseline; intended horizon/action or abstention; later outcome linkage and cost/model assumptions; session-end reconciliation; dropout/restart alerts; and measurable stop rules for stale data, skew, missing coverage, invalid math or persistence failure. Preserve gaps and rejected decisions. Never reconstruct missed decisions later as prospective observations.

Readiness evidence is a dry-run with archived/synthetic data and a clean restart. Future activation needs explicit project authorization and verified data rights/access; it remains read-only paper observation. Passing research or forward gates does not lift an existing scoring/release hold and does not authorize live orders or funds.
